# Inbox question schema

The execution session saves the question as UTF-8 JSON and submits it with `node inbox.mjs ask <campaignId> <question.json>`. The command prints the question ID. Do not edit `inbox.json` directly.

```json
{
  "kind": "decide",
  "title": "Choose a release window",
  "ticket": "#42",
  "askerThreadId": "asking-session-threadId",
  "askerLabel": "#42 execution session",
  "blocking": true,
  "background": ["Validation is complete; this ticket is waiting for a release window."],
  "options": [
    {"key": "today", "label": "Today", "consequence": "Schedule the release today", "recommended": true},
    {"key": "tomorrow", "label": "Tomorrow", "consequence": "Schedule the release tomorrow"}
  ],
  "multi": false,
  "recommendation": "Today is recommended; everyone involved is online.",
  "media": [{"path": "media/preview.png", "caption": "Preview"}]
}
```

Required fields:

| Field | Type and meaning |
| --- | --- |
| `kind` | `decide` for a decision or `accept` for acceptance |
| `title` | Nonempty string stating what needs a decision or acceptance |
| `ticket` | Ticket number as a string or integer; a closing summary may use `Closeout summary` (fixed identifier; localize the title) |
| `askerThreadId` | Nonempty string identifying the original asking session that receives the answer |
| `askerLabel` | Nonempty string naming the asker on the page |
| `options` | Required for decisions, with at least one option; omit for acceptance |
| `options[].key` | Nonempty string, unique among options |
| `options[].label` | Nonempty string shown as the choice title |
| `options[].consequence` | Nonempty string shown under the label; do not use `detail` or other undisplayed fields |

Optional fields:

| Field | Type and default |
| --- | --- |
| `id` | Letters, digits, underscores, and hyphens only; unique within the Campaign; generated by the service if omitted |
| `replaces` | ID of an earlier question this one revises. Accepted only while that question is `open`; the service then closes it with `replacedBy` set and the page moves the owner's unsent draft to the new question. Refused once the original has an answer or is closed |
| `blocking` | Boolean, default `false`. Set `true` only when the entire ticket has stopped |
| `background` | Array of strings, default empty array |
| `options[].recommended` | Boolean, default `false` |
| `multi` | Boolean, default `false`; whether a decision allows multiple choices. `true` requires at least two options |
| `recommendation` | String, default empty string |
| `media` | Array of media entries, default empty array |
| `media[].path` | Nonempty string identifying an existing readable file inside the Campaign directory; Campaign-relative paths are supported. Must not escape that directory or point outside it through a symlink |
| `media[].caption` | String; not displayed by default |

Acceptance questions use `kind: "accept"` and omit `options`. The page offers pass and rework; rework requires an explanation. Put images and videos in the Campaign directory before referencing them in `media`. Keep accepted media until the Campaign is archived.

The service fills in `createdAt`, `status`, `answer`, `history`, `times`, `forwardedTo`, `redo`, `notify`, `push`, `relay`, `closedNote`, `answeredBy`, `answeredVia`, and `replacedBy`; do not supply them in the question file. An answer is `{choices: [optionKey], note: "comment", images: [uploadReference]}`. Acceptance answer choices are `pass` or `rework`.

`answeredVia` records how the owner answered when attribution matters for chat relay: `web` for the page / trusted LAN, or `relay:<tokenId>` for a chat-relay bearer token. `answeredBy` stays `owner` in both cases (chat answers are owner answers). Orchestrator proxy answers keep `answeredBy: "orchestrator"` and do not set `answeredVia`.

`relay` records the latest outbound chat-relay dispatch when a Campaign has relay configured: `{state: "accepted"|"failed", at, event, attempts}`. Missing means relay is off or not yet attempted. No bridge URL, signing secret, or token is stored here.

## Chat relay (optional)

Default off. No `private/relays/<campaign>.json` (or `enabled: false`) means zero outbound relay traffic and no `relay` / `answeredVia` fields written on ordinary page use.

Outbound events (HMAC-signed JSON to the bridge URL): `question.opened`, `question.revised`, `answer.withdrawn`, `question.settled`. Schema `inbox-relay/1`. Secrets live only under `~/.agents/orchestration/private/relays/`.

Inbound reuses existing endpoints with optional fields:

| Endpoint | Extra fields |
| --- | --- |
| `POST /api/submit` | each `items[i].expect`: `{questionId?, status?, submissionId?}`; optional top-level `actor` (display name, max 64 chars, audit only) |
| `POST /api/item/<campaign>/<id>` | `expect.submissionId` on withdraw/retry |

Relay principal (`Authorization: Bearer <tokenId>.<secret>`):

- May call only submit / item / upload / `GET /api/campaign/<own>` / `GET /media/<own>/*` / health for its Campaign.
- Answers only `open` questions; already answered / replaced / closed / stale `expect` → **409** with `reason`: `answered` \| `replaced` \| `closed` \| `stale`, plus `status` / `answeredVia` / `submissionId` / `replacedBy` as applicable.
- Cannot overwrite an existing answer (web still can, last write wins per decision 45).
- May withdraw only answers whose `answeredVia` is this token; cannot post `messages`.
- `canManage` is always false for relay.

CLI (local admin token): `relay set\|status\|revoke\|resend <campaign> [id]`. `set` reads the bridge URL from stdin and prints the inbound token and signing secret once on a TTY.

Answer states are `open`, `saved`, `notified`, `read`, `forwarded`, and `closed`, in that order. Answers can be revised or withdrawn before the orchestrator handles them. Withdrawal returns the question to `open` with `withdrawalPending: true`; `pending` includes that cancellation until the orchestrator stops/corrects work based on the old answer and acknowledges it. Acknowledging a withdrawal leaves the question open. Ordinary `close` requires an answer; answering an open question requires explicit `--by orchestrator`, after pending cancellation is handled. Revising after forwarding marks `redo` and delivers the answer again. Closed questions are read-only; open a new question to reverse a closed decision. Comments are stored separately in `messages`. Acknowledge them after handling; close them before removing a Campaign.

On validation failure, the command returns the field name and reason without adding the question to the Inbox. Fix invalid media paths before retrying as well.

Owner attribution is stored as `answeredBy: "owner"`; `"orchestrator"` identifies an orchestrator answer. Older owner attribution is normalized on read and written in the new form on the next normal update. Reading alone does not rewrite the Campaign file or discard its answer/history.

`push` records the latest new-question dispatch result: `{sent: boolean, at: ISO timestamp, endpoints: number}`. `endpoints` counts successful push-service responses, not devices that displayed a notification. Batched questions share the result. Missing means queued/not yet attempted (or a legacy item). No subscription data or endpoint addresses are stored here. A false result includes no remote entry, no subscriptions, or all sends failing; owner receipt confirmation remains separate.

## Summary session fields

`GET /api/summary` includes owner-session flags used by the page:

| Field | Meaning |
| --- | --- |
| `loggedIn` | Request carries a valid `inbox_session` cookie |
| `canManage` | Owner may perform management actions that trusted LAN shares with cookie login (remove a Campaign; routing/quota/catalog writes). True when `loggedIn`, or when the request is on the main (non-remote) listener, `lanTrustSubnet` is true, and the client passes `allowedLan` / `lanTrustCidrs`. Remote entry still requires a cookie. |
| `routingSync` | Optional routing hub status: `{ version, updatedAt, peers: { [name]: { status, at, version, unsynced } } }`. Peers with `unsynced: true` did not accept the latest global push. |

The Campaign switcher shows **Remove** from `canManage`. Do not reuse `loggedIn` for that UI; **Add device** remains cookie-only. Routing settings writes reuse the same `canManage` check.

On a non-hub LAN page, peer Campaign rows also show **Remove** as a same-machine jump link (`?campaign=<id>&remove=<id>`), not a cross-origin write. That control is not gated by the viewing machine's `canManage`; enablement follows the peer summary's `removable` (unread → disabled with reason). Confirm, auth, and removal stay on the owning machine: it opens the dialog only when the Campaign exists locally, its `canManage` is true, and `removable` is true; otherwise it shows a hint. The `remove` query is stripped after handling; never auto-confirm. Hub/self rows still show **Remove** only from local `canManage`, and hub removal stays on-page via `api/remove-campaign`.

# Routing and capacity (`routing.json`)

Source of truth for dispatch routes and concurrency limits (decision 44). Files live under `INBOX_HOME` (default `os.homedir()`):

| Path | Role |
| --- | --- |
| `~/.agents/orchestration/routing.json` | Global layer, per-host overrides, quota, sync status |
| `~/.agents/orchestration/catalog.json` | Snapshot of T3 `orchestrator_capabilities` |
| `<campaign-dir>/routing.json` | Optional Campaign overrides (only changed fields) |

Secrets never go in these files.

## `routing.json` shape

```json
{
  "version": 1,
  "updatedAt": "2026-10-23T00:00:00.000Z",
  "global": {
    "routes": {
      "discussion": { "tiers": [{ "instanceId": "claudeAgent", "model": "claude-opus-5-5", "options": [{ "id": "effort", "value": "high" }] }, { "instanceId": "pi", "model": "cursor/claude-opus-5-5", "options": [{ "id": "thinking", "value": "high" }] }] },
      "design": { "tiers": [{ "instanceId": "claudeAgent", "model": "claude-opus-5-5", "options": [{ "id": "effort", "value": "high" }] }, { "instanceId": "pi", "model": "cursor/claude-opus-5-5", "options": [{ "id": "thinking", "value": "high" }] }] },
      "research": { "tiers": [{ "instanceId": "pi", "model": "opencode-go/deepseek-v4.1-flash", "options": [{ "id": "thinking", "value": "high" }] }, { "instanceId": "claudeAgent", "model": "claude-haiku-5-5", "options": [{ "id": "effort", "value": "high" }] }] },

      "review": { "tiers": [{ "instanceId": "pi", "model": "xai/grok-4.5", "options": [{ "id": "thinking", "value": "high" }] }, { "instanceId": "pi", "model": "cursor/grok-4.5", "options": [{ "id": "thinking", "value": "high" }] }, { "instanceId": "pi", "model": "opencode-go/deepseek-v4.1-flash", "options": [{ "id": "thinking", "value": "high" }] }] }
    },
    "limits": { "execution": 8, "design": 2 },
    "quota": {
      "pi/xai/grok-4.5": {
        "exhausted": true,
        "resumeAt": "2026-10-24T00:00:00.000Z",
        "markedBy": "orchestrator",
        "markedAt": "2026-10-23T12:00:00.000Z"
      }
    }
  },
  "machines": {
    "workstation-a": {
      "routes": { "code": { "tiers": [{ "instanceId": "pi", "model": "cursor/grok-4.5", "options": [{ "id": "thinking", "value": "high" }] }] } },
      "limits": { "execution": 4 }
    }
  },
  "sync": {
    "peers": {
      "workstation-b": { "status": "ok", "at": "2026-10-23T12:01:00.000Z", "version": 1 }
    }
  }
}
```

Route types: `discussion`, `design`, `visual`, `research`, `code`, `adjudication`, `review`, `housekeeping`. `housekeeping` is for the Campaign housekeeping session; a document without it resolves it from its own `research` route (the previous behavior) without rewriting the file. Each tier matches T3 `modelSelection`: `{ instanceId, model, options: [{ id, value }] }` with a nonempty `options` list (推理档位 required).

`design` covers all design work, including form, layout, motion, and new visual decisions. `visual` covers visual implementation of an established design: 3D, materials, rendering, and visual adjudication. Non-visual adjudication stays on `adjudication`. Resolve model choices from Inbox settings.

Pre-visual global documents receive the built-in `visual` route in memory on load; other routes, version, and disk contents remain unchanged. A subsequent sanctioned write serializes the normalized document, including the supplied visual route; this also applies to quota and machine-layer writes. Upgrade every receiving service before enabling routing writers, then persist owner choices through `PUT /api/routing`. Explicit null or malformed visual routes are rejected.

Effective resolution: **global → host → Campaign**. Only overridden fields are stored on host/Campaign layers. On machine and Campaign patches, a field value of `null` deletes that override (`routes.<type>: null` or `limits.execution|design: null`) so the effective value falls back to the parent layer. Global patches reject `null`. Exhausted quota keys (`instanceId/model`) are skipped when resolving. Concurrency limits may only tighten down the stack. Each resolved tier and limit records its `source` (`global` / `machine` / `campaign`).

Writes to `routing.json` use atomic replace and require `expectedVersion` matching the current document `version` (HTTP 409 / “请重新加载后再改” on conflict). Global and quota writes bump `version` and `updatedAt`. Host-layer edits update `updatedAt` only (they stay on that host and do not bump the shared sync version). Campaign overrides live in the Campaign directory and are not versioned with the shared document. `routing-import` seeds the built-in 2026-10-23g table via `seedBuiltinRouting()`; it does not read `AGENT_RULES.md`.

## Routing change events

Every routing or model-settings write that actually changes a layer notifies the Campaign orchestrators through the transports that already exist for Inbox answers and execution reports. Triggers: `PUT /api/routing` (the settings page and other API callers), `POST /api/quota`, an accepted peer `POST /api/routing/sync`, and the CLI writers `quota mark|clear` / `routing-import --force`. A save that leaves routes, limits and quota identical emits no event, even though a global write may still bump the document `version`; a fresh `routing-import` with no existing file matches the built-in table and also stays silent.

- Scope: `global` and `machine` changes notify every Campaign registered on this machine; a `campaign` change notifies only that Campaign. Each Campaign delivers according to its `orchestratorKind` in `campaign.json`.
- `t3-thread`: POST to the Campaign's existing answer-notification webhook (`private/webhooks/<campaignId>.url`) with `X-Inbox-Event: routing-change` and `X-Orch-Queue: 1`. No webhook configured → delivery result `unconfigured`.
- `external`: POST the signed queue-only report body to `private/orchestrators/<orchestratorRef>.json` with the orch-report headers `X-Orch-Signature` / `X-Orch-Timestamp` / `X-Orch-Id` / `X-Orch-Queue`, so `report.mjs verify --campaign-dir <campaign> --body-file <body> --headers-file <headers>` prints `{"ok":true}`.
- Failure: each delivery is logged as `{"event":"routing-event","scope","campaign","mode","result","status?"}` only — never the endpoint, signature or fetch error text — and the routing write still succeeds.
- `changedBy` is `ui` when the request carries a browser `Origin`, `api` for other HTTP callers, `cli` for the CLI writers, `sync` for a peer's accepted global snapshot, or a whitelisted `changedBy` field in the request body.

Public body (per Campaign, no tokens, URLs, webhook addresses or signature material):

```json
{
  "schema": "orch-report/1",
  "event": "routing-change",
  "campaign": "example-campaign",
  "phase": "routing-change",
  "summary": "Routing change global v22 by ui: routes code (code: pi/xai/grok-4.5/thinking=high -> pi/cursor/grok-4.5/thinking=high)",
  "routingChange": {
    "scope": "global",
    "campaignId": null,
    "machine": null,
    "changedBy": "ui",
    "changedAt": "2026-10-29T04:00:00.000Z",
    "routingVersion": 22,
    "routes": [
      {
        "type": "code",
        "before": [{ "instanceId": "pi", "model": "xai/grok-4.5", "options": [{ "id": "thinking", "value": "high" }] }],
        "after": [{ "instanceId": "pi", "model": "cursor/grok-4.5", "options": [{ "id": "thinking", "value": "high" }] }]
      }
    ],
    "limits": [{ "key": "execution", "before": 8, "after": 6 }],
    "quota": [{ "key": "pi/xai/grok-4.5", "before": null, "after": { "exhausted": true, "resumeAt": null } }]
  }
}
```

## `catalog.json`

```json
{
  "capturedAt": "2026-10-29T12:00:00.000Z",
  "capabilities": {
    "providers": [
      {
        "providerInstanceId": "codex",
        "displayName": "Codex",
        "models": [
          {
            "id": "gpt-6.1-sol",
            "options": [
              {
                "id": "reasoningEffort",
                "values": ["low", "medium", "high", "xhigh", "max", "ultra"],
                "default": "low"
              }
            ]
          }
        ]
      },
      {
        "providerInstanceId": "pi",
        "displayName": "Pi",
        "models": [
          {
            "id": "openai/chat-latest",
            "label": "Chat Latest",
            "options": [
              {
                "id": "thinking",
                "values": ["off", "minimal", "low", "medium", "high"],
                "default": "medium"
              }
            ]
          }
        ]
      }
    ]
  }
}
```

`catalog-write` / `POST /api/catalog` store the live `orchestrator_capabilities` payload under `capabilities`. Input may be one capture or an array of captures (base capture plus `search` lookups); arrays are merged by `providerInstanceId` and model `id` so omitted models from search stay available on the page. Before writing, every `instanceId/model` referenced by the global, machine and registered Campaign routing layers must be present; otherwise nothing is written and the CLI fails (HTTP 409 with `missing[]`) listing them. `--allow-missing` (HTTP `allowMissing: true`) writes anyway, prints a warning and returns `missing[]`. Validation and the settings page read `providers[].providerInstanceId`, `models[].id` (and optional `models[].label`), `models[].options[].id`, and for selects either `models[].options[].values` (string or boolean arrays, with optional `default`) or the legacy nested `models[].options[].options[].id` list. Boolean options may use `type: "boolean"` or a boolean `values` array. The earlier invented top-level `providerInstances[].id` shape is not accepted; an unrecognized snapshot is treated like a missing catalog (`catalogCheck: "missing"`, unchecked). When a recognized catalog is present, writes that introduce unknown `instanceId` / `model` / option values are rejected.

## CLI (reads/writes files; no admin server required)

| Command | Purpose |
| --- | --- |
| `node inbox.mjs routing-import [--force]` | Write the built-in 2026-10-23g global table (limits 8 / 2). Refuses if the file exists unless `--force` |
| `node inbox.mjs catalog-write [--allow-missing]` | Read `orchestrator_capabilities` JSON (or an array of captures) from stdin into `catalog.json`; refuses if routed models are missing |
| `node inbox.mjs route <campaignId> <type>` | Print effective ordered tiers for one type (JSON) |
| `node inbox.mjs routes [campaignId]` | Print all types plus effective limits |
| `node inbox.mjs quota mark <instanceId/model> [--resume <ISO>] [--by orchestrator\|owner]` | Mark exhausted |
| `node inbox.mjs quota clear <instanceId/model>` | Clear exhausted |

`quota mark|clear` and `routing-import --force` write routing directly (no running server) and also emit the routing change event with `changedBy: "cli"`; the JSON output carries a `routingEvent` delivery list (Campaign id, mode, result only, never endpoints).

## HTTP API (used by the Dispatch settings page, `?view=routing`)

Management writes use `canManage` from `access.mjs` (same helper as Campaign removal): valid login cookie, or trusted LAN when `lanTrustSubnet` is true. Remote always needs a cookie. Cross-site `Origin` / `Sec-Fetch-Site` checks still apply.

| Method | Path | Purpose |
| --- | --- |
| `GET` | `/api/routing?campaign=&machine=` | Layers, effective values, catalog presence, sync |
| `PUT` | `/api/routing` | Body `{ layer, machine?, campaign?, expectedVersion, patch }`. Campaign layer requires registered `campaign` id. Global/host writes require `expectedVersion`. Global writes fan out to peers. Emits routing change events to affected Campaign orchestrators |
| `POST` | `/api/routing/sync` | Peer ingest of a signed global snapshot (`X-Inbox-Routing-Sync`) |
| `GET` | `/api/catalog` | Catalog snapshot |
| `POST` | `/api/catalog` | Replace catalog (`{ capabilities, capturedAt? }`) |
| `POST` | `/api/quota` | `{ key, exhausted\|action, resumeAt?, markedBy?, expectedVersion }` then sync; emits a routing change event |
| `GET` | `/api/route/<type>?campaign=` | Effective route for one type; `type=all` or `?all=1` for all |

Hub editing of another host's host layer forwards `PUT /api/routing` to that peer's `lanUrl` / `publicUrl`. Global quota lives only in the global layer and syncs with it.


# Ticket board (Progress tab, read-only)

The Inbox **Progress** tab (`?campaign=<id>&tab=progress`) shows a Campaign's tickets as a read-only board (structure per the finalized kanban design spec v2, styled with the Inbox design tokens). It replaces the old progress list. It never writes: no drag, edit or status change; owner items link to their question in the Decisions or Reviews tab. Column and filter choices persist in `localStorage` (`pmKanban.v2.columns`, `pmKanban.v2.filters`); theme and language follow the Inbox. The old `kanban.html?campaign=<id>` link redirects to the Progress tab, keeping `campaign` and `machine`.

`GET /api/kanban/<campaignId>` is the only endpoint. Any other method returns **405** with `Allow: GET`; an unregistered Campaign returns **404**. Access follows the existing login rules (cookie on the remote listener; loopback and trusted LAN as elsewhere). A relay bearer token is rejected with **403**.

The server reads, and never writes:

| Source | Use |
| --- | --- |
| `campaign.json` `tickets[]`, `milestones` | Cards, stage, branch/commit, `blockedBy`, explicit `issue` |
| `inbox.json` `items[]` with `status: "open"` | `needsOwner`, `ownerItems` |
| `events.log` (last 256 KB) | Latest line per ticket: `lastReport`, `lastReportAt` |
| `tickets/<id>.md` (exact `<id>.md` names; `*.bak-*` and symlinks skipped) | Title fallback, `summary` (`说明：` line or first paragraph), spec version |
| `gh issue list --repo <owner/repo> --state all --limit 2000 --json …` | GitHub issue title, state, milestone, labels, assignees |

Milestones come from each issue's `milestone` field; the version is the milestone title's version number. The drawer shows **未挂 milestone** for a linked issue without one. The GitHub repo comes from `campaign.json` `github` (`owner/repo`), else `github.com/<owner>/<repo>` or `clone of <owner>/<repo>` in `project`. Issue results are cached for five minutes in `~/.agents/orchestration/cache/kanban/<campaignId>.json` without issue bodies. When `gh` fails, the board uses the cache and reports `github.stale: true` with the cache time; a failed call is retried after one minute. Raw `gh` errors are never returned.

Issue ↔ ticket mapping uses explicit markers only, in this order: the ticket's `issue` field, an issue label `v<N>:<ticketId>` (for example `v4:P41`), an issue body line `Campaign: <campaignId>/<ticketId>`. Bare `P9` text is ignored.

Stage → column (`status`):

| `stage` | `status` |
| --- | --- |
| `未开始` | `queued` |
| `执行中` | `running` |
| `卡住：<reason>`, `等你决定 <id>`, `等你来讨论` | `blocked` (`blockedReason` carries the reason) |
| `待核实`; `已交付` with a pending `acceptance` / `deviceAcceptancePending`; `已交付…待核实…` | `verify` |
| `已交付` | `delivered` |
| `返修` | `rework` |
| `待合并`; `已交付` with `mergeRequest`; `已交付…待合并…` | `merge` |
| `已合并`, `已合入…`, `已合主线…` | `merged` |
| `已关闭`, `移出范围` | `closed` |
| anything else | `status` field (`closed`/`done` → `closed`, `merged` → `merged`), else `queued` |

Response fields per ticket: `id`, `title` (GitHub issue title when that issue backs only this ticket, else the Campaign title, else the ticket file heading; never with the leading `id：`), `summary`, `kind`, `stage`, `version`, `versionSource` (`milestone` \| `spec` \| null), `machine` (ticket value, else this Inbox's machine name), `status`, `needsOwner`, `ownerItems[]`, `blocked` (status `blocked`, or a `blockedBy` ticket not yet delivered/merged/closed), `blockedReason`, `dependsOn[]`, `threadState` (`running` \| `idle` \| `waiting` \| `suspended` \| `notStarted` \| `ended`; derived from status and whether a thread is recorded, because the Inbox has no read-only source for live T3 thread state), `branch`, `commit` (7 chars), `lastReport`, `lastReportAt`, `updatedAt` (`since`), `issue` (`{number, title, state, url, milestone, labels[], assignees[]}` or null), `conflict` (`issueClosed` \| `issueOpen` \| null), `orchestratorSide` (no issue), `missingIssue` (deliverable ticket for this repo, not yet merged or closed, with no issue). Top level: `campaign {id, title}`, `generatedAt`, `github {repo, fetchedAt, stale, error}` (`error`: `no-repo` \| `github-unavailable` \| null), `ownerCount`, `conflictCount`.

GitHub wins on conflicts but the board never corrects data: a closed issue whose ticket is not merged/closed, or an open issue whose ticket is merged/closed, gets the yellow-dot **状态不一致** chip, and the header shows the total as its own yellow-dot chip next to the snapshot time. Tickets without an issue get the dashed neutral **编排侧** tag; deliverables that should have one also get the neutral **缺 issue** tag. Both tags have no dot, because dots mean status and red means blocked (owner choice: chips on the cards, no extra lane; designer review: neutral tags). When nothing waits for the owner, the notice bar turns neutral and reads **暂无待你确认**. Without GitHub data (no repo, or `gh` failed with no cache) these markers are off; a successful empty result counts as data.
