# Patrol

The scheduled task prompt contains only `/orchestration patrol <campaign>`, with a fallback run every 60 minutes. First merge queued messages as described in SKILL.md and combine accumulated patrol triggers into one run. If a patrol trigger is merged into another long turn, that turn must still complete item 3 below and record the patrol. After quota recovery, also handle reports and answers accumulated during the outage.

## Check each run

Check and notify review route changes as specified in INBOX.md, including retries for unverified deliveries.

If the Campaign is no longer registered, use SKILL.md's removed-Campaign handling and stop this patrol. Handle `withdrawalPending` entries before ordinary answers per INBOX.md. Close handled comments after acknowledging them, so they do not unnecessarily block owner removal.

0. **Pre-patrol crosscheck.** When the project provides a read-only ledger×GitHub×T3 crosscheck command, export current `t3_thread_list` pages (all statuses) and open GitHub issues, then run that command against `campaign.json`, `events.log`, and the Campaign `deliveries/` directory. Use the one-line-per-item report before changing stages, dispatching, reclaiming worktrees, or reporting how many tickets are running. The command is read-only: do not let it write the ledger, GitHub, or T3. Missing exports are unknown, not proof a thread died.
1. **Service and answers.** Run `node inbox.mjs health`; if unhealthy, restart once as described in INBOX.md and check again. Run `pending <campaignId>`. Prioritize answers saved more than 15 minutes ago that remain unread, and handle them as described in INBOX.md. For ordinary questions: ack, handle, forward, implement, then close; forward redo answers again. The orchestrator handles acceptance questions itself and skips forward; close only after merging, passing checks and successfully pushing. Read inbox.json to verify that forwarded answers have been implemented; ack messages after handling them. Retain media until archiving. If a question shows `relay.state: failed`, run `node inbox.mjs relay resend <campaignId> <id>` once and re-check the `relay` field; do not loop. Chat-relay answers still use the same pending path (`answeredVia` may be `relay:<tokenId>`).
2. **Registered child tasks.** For every unprocessed registered taskId, call task_status once. If project settings provide an offline patrol reconciliation command, export the results and defer all result handling and consumption to item 3; do not mark them processed first. Otherwise handle completed unprocessed results during this turn and mark them processed, handle failed or blocked tasks under the handoff rules, and retain tasks still running. Do not loop waiting for results in this turn.
3. **Execution tickets, housekeeping, and deliveries.** When the project provides an offline patrol reconciliation command, follow Offline reconciliation below instead of the direct handling/sending path in this item: export first, reconcile, refresh, handle once, then confirm consumption. For projects without that entry only: Use t3_thread_list / t3_thread_read to check dispatched ticket status and the latest message. If the most recent turn is interrupted, failed or cancelled and the ticket has not been delivered, send one “resume from the interruption point” message using `mode=auto` during this turn, and record the interruption time in events.log. **Outstanding HK items:** list every `HK-*` in `awaitingReports` and any `hk-sent` in events.log without a later `hk-done` for the same id (no separate HK todo file; HOUSEKEEPING.md). Treat those the same way for the housekeeping thread: interrupted/failed/cancelled with no report → one continue on the **current task** (`mode=auto` if idle/terminal, `steer` if still running — not a new-matter queue); log `hk-continue` or replace and log `hk-replace`. Check the latest turn of every ticket in progress. Do not filter t3_thread_list to running threads only, because interrupted threads would be omitted. Activity in a RECORD or lock file does not count as checking thread status. Replace threads that cannot resume as described in DISPATCH.md. A thread ending without a report is not completion: inspect its branch and delivery records. An idle ticket whose last message names subagents it waits for is waiting, not stalled; if those subagents show completed in t3_thread_read and no later turn followed, send one “continue: your subagents finished” message using `mode=auto`. Investigate blockers after 30 minutes without activity. For tickets awaiting answers, verify the worktree still exists; if missing, restore it from the original branch. Lightly check delivered tickets by SHA, clean workspace and existence of every file in the artifact list; do not rerun validation.
4. **Resources and disk.** Read the Campaign-pinned project resource adapter and use its status entry to inspect lanes, holding processes and start times. Only use lease.mjs status when that is the selected adapter; unselected commands in PROJECT.md are reference examples. Processes acquire and release resources themselves. Do not send acquisition/release requests or allocate resources through a ledger. The orchestrator must not acquire or hold device locks for itself. **When housekeeping is enabled:** only read free space on the configured volumes; if below the warning threshold and there is no open `disk` request / `HK-*` disk entry in `awaitingReports`, send one **new-matter** `disk` request to housekeeping (`queue`, or `auto` if idle; `scripts/worker-send.mjs --hk-new-matter`). Do not clean or list candidates yourself. **When housekeeping is not enabled:** if disk space is low, verify and clean only leftover worktrees, temporary directories and build artifacts for this Campaign's tickets that have been merged and successfully pushed; record this in events.log. If space is still insufficient, submit an Inbox question listing the largest items for the owner to decide. Do not touch running tickets, other Campaigns or user data.
5. **Frontier.** Dispatch eligible undispatched tickets when slots are available: all blockers must be closed or merged into the main branch. Read the effective execution and design limits with `node inbox.mjs routes <campaignId>` before filling them; do not assume the built-in default.

Done when: health is checked, no answers remain unforwarded, registered taskIds are checked, total resource usage is inspected, and pending deliveries and frontier tickets are handled. Delegate long-running work with delegate_task and end the turn; do not run builds or tests or wait in place. Project settings may explicitly allow post-merge checks taking less than one minute to run directly in the orchestrator's turn; all other checks remain delegated. Push and close tickets only after post-merge checks pass.

## Offline reconciliation

When project settings provide an offline patrol reconciliation command, export the current all-status t3_thread_list pages and t3_thread_read results for every dispatched ticket. Include registered task_status results, verified parent waiting-run bindings and child terminal runs, delivery observations tied to runIds, and resource observations from the project's existing lock adapter. Refresh these observations each patrol; missing exports are unknown, not evidence that a thread died or a resource is free. Run the project command to produce the ticket table and this turn's todo list. The command itself reads files only and sends no messages.

Handle the latest Inbox answers first, then batch the todo list by ticket (and outstanding `HK-*` items). Before sending a continuation, re-read its latest run: a new or active run supersedes the old continuation. A terminal run without a registered delivery requires branch/delivery inspection; completed child work requires evidence that no later parent run followed. An old updatedAt alone never proves termination. Follow the current provider message rules in SKILL.md (never-queue for running workers: `steer` while running, `auto` if idle/terminal; HK new matter → queue with `--hk-new-matter`, HK current-task → steer/auto; post-send verify active run not composer queue for workers and HK current-task) and project settings. Keep the existing 60-minute fallback.

After actually handling a result or successfully sending one continuation, confirm the corresponding runIds/taskIds and separate delivery identities in the project's local patrol-processed.json. Merely displaying a report does not consume it. Save the merged state through a separate new file after a successful command, before clearing consumed queue entries; never redirect output over an input file. If state saving fails, retain the notification and repair the record before resending. This local file deduplicates consumption only; campaign.json and events.log remain owned by the orchestrator, with their existing purpose. Done when all observed terminal results, pending deliveries and continuation gaps have been handled or explicitly recorded as unresolved, and repeating the same observations produces no duplicate continuation.

## Records

When anything changes, update campaign.json and append to events.log. Name tickets as `id：short title` in events and any owner-facing lines (DISPATCH.md). Running-count reports follow item 0 (fresh crosscheck / thread list); do not reuse a stale count. The web page reads campaign.json for progress; do not send separate refresh messages. With no changes, record only “patrol, no changes”. Once all tickets are delivered, close the Campaign as described in SKILL.md.

If all tickets are delivered and the closeout question is approved but the Campaign is still registered, unregister it as described in Close out.

Done when: each fact is recorded in one place, handled queue entries are cancelled, and there are no duplicate messages or repeated validation.
