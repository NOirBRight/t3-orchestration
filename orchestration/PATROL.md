# Patrol

The scheduled task prompt contains only `/orchestration patrol <campaign>`, with a fallback run every 30 minutes. First merge queued messages as described in SKILL.md and combine accumulated patrol triggers into one run. If a patrol trigger is merged into another long turn, that turn must still complete item 3 below and record the patrol. After quota recovery, also handle reports and answers accumulated during the outage.

## Check each run

1. **Service and answers.** Run `node inbox.mjs health`; if unhealthy, restart once as described in INBOX.md and check again. Run `pending <campaignId>`. Prioritize answers saved more than 15 minutes ago that remain unread, and handle them as described in INBOX.md. For ordinary questions: ack, handle, forward, implement, then close; forward redo answers again. The orchestrator handles acceptance questions itself and skips forward; close only after merging, passing checks and successfully pushing. Read inbox.json to verify that forwarded answers have been implemented; ack messages after handling them. Retain media until archiving.
2. **Registered child tasks.** For every taskId in campaign.json tasks whose result has not been processed, call task_status once. Handle completed, unprocessed results during this turn and mark them processed. Handle failed or blocked tasks under the handoff rules; retain the registration for tasks still running. Do not loop waiting for results in this turn.
3. **Execution tickets and deliveries.** Use t3_thread_list / t3_thread_read to check dispatched ticket status and the latest message. If the most recent turn is interrupted, failed or cancelled and the ticket has not been delivered, send one “resume from the interruption point” message using `mode=auto` during this turn, and record the interruption time in events.log. Check the latest turn of every ticket in progress. Do not filter t3_thread_list to running threads only, because interrupted threads would be omitted. Activity in a RECORD or lock file does not count as checking thread status. Replace threads that cannot resume as described in DISPATCH.md. A thread ending without a report is not completion: inspect its branch and delivery records. Investigate blockers after 30 minutes without activity. For tickets awaiting answers, verify the worktree still exists; if missing, restore it from the original branch. Lightly check delivered tickets by SHA, clean workspace and existence of every file in the artifact list; do not rerun validation.
4. **Resources and disk.** Run `node <skill-directory>/scripts/lease.mjs --project <project-settings.md> status` to inspect total pool usage: lanes, holding processes and start times. Processes acquire and release resources themselves. Do not send acquisition/release requests or allocate resources through a ledger. If disk space is low, verify and clean only leftover worktrees, temporary directories and build artifacts for this Campaign's tickets that have been merged and successfully pushed; record this in events.log. If space is still insufficient, submit an Inbox question listing the largest items for the owner to decide. Do not touch running tickets, other Campaigns or user data.
5. **Frontier.** Dispatch eligible undispatched tickets when slots are available: all blockers must be closed or merged into the main branch. Default to no more than eight tickets running at once.

Done when: health is checked, no answers remain unforwarded, registered taskIds are checked, total resource usage is inspected, and pending deliveries and frontier tickets are handled. Delegate long-running work with delegate_task and end the turn; do not run builds or tests or wait in place. Project settings may explicitly allow post-merge checks taking less than one minute to run directly in the orchestrator's turn; all other checks remain delegated. Push and close tickets only after post-merge checks pass.

## Records

When anything changes, update campaign.json and append to events.log. The web page reads campaign.json for progress; do not send separate refresh messages. With no changes, record only “patrol, no changes”. Once all tickets are delivered, close the Campaign as described in SKILL.md.

Done when: each fact is recorded in one place, handled queue entries are cancelled, and there are no duplicate messages or repeated validation.
